# 采用条件与实现边界

## 决定来源

2026-11-07 用户明确要求“对于 pakka 的情况，配置默认启用 pakka-dynamite”。这替换普通产品的策略选择，结束将 Pi 原生 compaction 和 Dynamite 作为默认方案待二选一的讨论。独立 SDK 的宿主装配职责与固定 headless 配对未被此决定替换。

评估基线为 PR #2 合并后的 `dev@e7c938ef3b7c2005ef9db319bd84598c25ab8b23`。该版主 Runtime 关闭原生自动 compaction，默认 `createLocalProduct` 尚未装配 Dynamite。Compresser 与持久化能力已有自己的实现和记录；它们不能证明默认产品已经接通。

## 已采用的关系

普通产品的上下文管理使用 Dynamite。bootstrap 管理策略服务、业务 Conversation 绑定以及 Compresser 存储；每次压缩仍受模型、来源、辅助预算和采用权限约束。产品默认启用不等于启动时立即产生压缩请求，也不授予任意模型或 worker 新权限。

同一业务 Conversation 的上下文改写由单一策略所有者协调，避免原生自动 compaction 与 Dynamite 同时独立改变上下文。读取 UI 和配置管理在模型/压缩配置暂不可用时仍可访问，策略可用性与工作状态需要可见。

核心 SDK 保持宿主可组合性。实际使用的 Dynamite 版本与归档在实现时固定并验证；历史的静态初始成员配对不被文字变更扩展为动态成员支持。

## 实现前需要具体化

- 压缩模型如何从原生模型目录选取；默认使用哪些模型、是否跟随业务模型，需要单独设计。
- 触发阈值、窗口、辅助预算及不足时的用户操作。
- 新建、重开、fork、动态成员和独立 worker 的绑定与所有者，Compresser 启停及故障域。
- 显式覆盖策略的配置入口与作用域。
- 固定跨仓依赖、安装消费和长任务的验证材料。

这些是默认 Dynamite 下的装配问题；本次没有采用具体数值、推理模型或重试政策。

## 同轮调查的历史依据

以下是对既有边界的解释与建议，不是本 change 的产品实现范围。

- `3656b308561bb6aa9c9b35cb6bd12a7111c8287d`（2026-10-13）的 MAS design 明确写到 delivery records 可能增长，因此设置 finite maxDeliveries、每收件人 maxPending，并避免不安全淘汰；M2 全 Session 保留去重身份。它解决受控接纳与重试正确性，没有设计可持续保留和回收流程。原文见[当时 design](https://github.com/mapleluvr/pakka/blob/3656b308561bb6aa9c9b35cb6bd12a7111c8287d/openspec/changes/archive/2026-10-13-same-session-mas/design.md)。
- `38bfb8ac461f1bdb0060e91a4eb1a2bc5931d3a8`（2026-10-15）在 WebUI 装配中选择 maxDeliveries=512、maxPending=32。此次追查没有找到 512 对应用户任务量或性能测量的记录。精确数值是实现配置，不应推导为 Session 的产品寿命需求。
- 同一 WebUI 提交要求 finite body/concurrency 与 bounded SSE，默认把 maxConnections=32 用于全部在途 HTTP。当前本地探针确认 32 条 SSE 占满后管理 RPC 返回 503，释放一条即恢复。有限资源有依据，但没有找到“观察流可以耗尽全部管理容量”的产品要求。

建议后续从原请求可核对、存储/内存可持续，以及查看和重连不阻断发送/停止/管理等行为设计。具体保留政策、连接分配与支持规模仍待采用，不能用调大常数代替生命周期设计。

## HTTP 容量的初始估算（候选）

用户随后要求给出可直接估算的数值。针对本地或小团队的候选工作负载，建议先分别设置 32 条 SSE 观察流和 16 个短请求并发位，而不是把所有请求放在一个 48 位计数器中。这是用于验证的初值，未测得支持上限，也不是已采用的产品规模承诺。

估算假设：最多 5 名同时在线人员，每人 3 个活动页面；现有普通页面对当前所选 Conversation 建立一条 EventSource；断线重连时预留一倍短暂重叠。观察连接需求为 `5 × 3 × 1 × 2 = 30`，取 32。

短请求独立估算：峰值 20 请求/秒、平均在途时间 0.2 秒时，平均并发为 4；再给 4 倍瞬时突发余量，取 16。到达率和延迟是待验证假设，20 请求/秒包含前端状态读取、设置和人工操作，不是 20 次人类输入/秒。高分位延迟另外用于 SLO，不能把平均并发估算当作尾延迟保证。

需测量：同时在线人员和活动页数、每页实际订阅数、重连重叠时长、短请求峰值到达率/平均与 p95 延迟、快照字节数及生成频率、每流内存/CPU、慢客户端积压。当前每流默认 100 ms 读取一次；32 条流理论上可触发每秒约 320 次观察读取，但不是实测吞吐，也不代表每次都发送全量网络数据。连接数初值必须与这一成本一起验证。

产品需求建议为：观察满载时管理/取消仍可用，单条慢流有界积压，切页/断线/撤权及时清理，仅重建观察而不重放变更。短请求池自身满载或事件循环被长操作占用时也需保护关键操作；分开计数只解决当前已复现的 SSE 占满问题，不能单独证明所有压力下可用。

## 验证安排

当前阶段检查文档、引用与 OpenSpec 结构。实现阶段用隔离的本地 provider 验证默认装配、辅助预算、精确采用、重开与安装消费；真实长任务验证按届时明确授权的模型、材料和调用范围执行。
