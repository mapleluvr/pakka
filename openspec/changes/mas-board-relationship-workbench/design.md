## 1. 这块界面参与什么工作

用户打开 MAS Board，是为了看清一次协作里有哪些 Conversation，它们怎样产生、怎样交流、现在进行到哪里；需要参与某个成员时，能进入它的完整 Conversation，再回到原来的观察位置。

Board 由 MAS DevPack 的 WebUI facet 通过普通扩展槽提供。节点、交流记录和操作都使用宿主已经绑定的人员与资源权限。单独安装这一界面可以观察协作；模型工具由宿主另行装配。

我们以一个已装配 MAS 服务所绑定的 Runtime／Session 和 MAS 名册为第一版观察范围。当前 namespace 是名册隔离标识，图的服务端数据源在装配时确定。画布上的一个分组、一个 namespace、一个 Agent，各有各的身份与用途。

一次性工作的用户使用方式是普通 Conversation：新建、使用、用后删除。当前工作区已经提供归档／恢复；实际删除的契约与实现单列在第 8 节。MAS 内部仍可创建具有内部寿命的 Conversation；可见性和可读历史由服务端决定，用户入口围绕普通 Conversation 操作组织。

## 2. 实体、用语和例子

### 2.1 实现中实际存在的对象

| 对象                   | 在现有实现中的作用                                                               | 在 Board 中怎样使用                                            |
| ---------------------- | -------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| Durable Session        | 承载 Conversation、原生任务与持久化的运行容器                                    | 构成绑定数据源的身份边界；不画成 Agent                         |
| Conversation           | 原生对话、历史及独立模型／cwd 配置的资源                                         | 一个可观察、可进入的节点所对应的资源                           |
| MAS Member             | 名册记录，含 key、ref、owner、lifetime、phase                                    | 提供成员资格和管理元数据；不另建模型实例                       |
| ConversationRef        | key、sessionId、conversationId、incarnation、profile 组成的定位引用              | 读取和操作使用服务端核对后的当前引用；序列化字段本身不授予权限 |
| Catalog／MAS namespace | 服务端指定的名册与投递记录隔离范围                                               | 决定当前图的数据来源，不等同于 Session 或项目目录              |
| DeliveryReceipt        | 一次投递的身份、发送端、接收端和结果元数据；当前公开回执不带正文、时间或 replyTo | 用于核对投递；完整交流日志还需补足观测数据                     |
| ExtensionOperation     | 一次扩展调用的外层结果                                                           | 与内部投递／任务结果并列核对                                   |
| 原生 task              | 执行与寿命管理单位                                                               | 支撑活动观测；不作为 Agent 节点                                |

`DeliveryReceipt` 当前的精确字段见 `packages/agent/src/types.ts`。模式与正文属于投递输入，能够从受控记录取得时才发布；不能因为输入类型有字段就声称回执也有。

### 2.2 面向使用者的词

- **Agent**：Conversation 参与这次协作时的界面称呼。节点打开同一份 Conversation。
- **创建关系**：记录支持的“哪个 Conversation 创建了哪个 Conversation”。
- **通信**：有明确发送端、接收端的投递。发起方式另行说明。
- **交流记录**：将已授权的投递、正文、状态及已知关联组成可阅读的记录。
- **活动**：某一时刻的真实运行观测，例如模型输出或工具执行。

主界面使用 Conversation 名称。当前 MAS DTO 只有成员 key、没有普通工作区的人类标题；需要补一个受控名称读取，缺少名称时清楚显示成员标识。名称是展示文本，资源定位仍使用引用。

### 2.3 示例的边界

下文 A、B、C、D 是别名，不是数据表、接口字段、权限身份或约定的真实 key。示例消息和状态是构造材料。实现、测试与草图都应显式标明使用的是构造数据还是原生运行记录。

## 3. 一段贯穿界面的协作

**设计例子：**A 创建 B、C，B 创建 D。B 向 C 发送一个问题，C 在另一条投递中回答；这两条投递有明确记录的回复关联。

用户打开图，可以沿创建线看出 A、B、C、D 的结构，沿通信线看到 B 与 C 的往来。点中 B→C 的计数，交流区显示该方向的投递和原问题。选择“双方往来”，再看到 C 的回答以及被回答的原记录。

用户选中 C，详情展示实时活动和“打开 Conversation”。进入后，模型选择仍在输入区，cwd 入口仍在 Conversation 标题下；Settings 继续承担用量和凭据等既有设置。返回 Board 后，C 的选择、画布位置和交流筛选保持。

用户隐藏 B→C，随后打开“已隐藏”恢复它。隐藏过程中原投递、任务和交流查询均维持各自状态。

这个例子使设计可以被走通。当前 `MasClient.reply()` 会依据原回执确定回投目标，但**没有持久保存 replyTo**；已有旧记录只能显示可证明的方向，完整问答关联是本轮新增观测需求。

## 4. 身份和三种关系

### 4.1 一个资源、一张卡片

在一个绑定的数据源内，用 Session ID 与 Conversation ID 识别逻辑节点；作用域同时包含宿主绑定的数据源身份。相同字符串出现在另一个 Runtime 或另一安装环境时，不自动合并。

名册中的 key 用于该名册定位；profile 说明基础配置；incarnation 表示当前可用引用的一次身份更新。独立切换模型／cwd 后，原引用失效，图形位置和选中资源可以延续，由服务端重新解析当前引用。

第一版不引入浏览器任意选择远端 endpoint 的数据源切换。以后汇聚多个获准来源时，需显式扩展来源身份及授权契约。

### 4.2 创建、管理、历史来源

| 问题             | 依据                        | 呈现位置                         |
| ---------------- | --------------------------- | -------------------------------- |
| 谁创建了它？     | 实际创建来源记录            | 默认创建关系层                   |
| 谁拥有管理能力？ | 受控 capability／owner 关系 | 详情；有需要时提供独立管理关系层 |
| 历史从哪里继承？ | 原生 fork 来源及 entry      | Conversation／详情中的历史来源   |

当前 `WorkbenchMember.parent` 是 owner 匹配出的管理来源，不是现成的创建事件。`ownerTaskId` 表示内部寿命归属，也不是人类所有者。

第一版由已绑定 MAS 名册的成员构图。现有 `MasClient` 对非空 source 会核对当前名册成员；普通工作区任意 Conversation 不能直接充当当前 MAS 操作的来源。它们进入完整 Conversation 界面依赖下文的通用解析。以后若支持跨名册来源，需扩展来源记录和授权契约；资料缺失时图仍以已获准的节点为范围，不从 owner／principal 字符串猜出额外节点。

### 5.1 节点

沿用现有**直角 Conversation 框**。标题、状态、片段三层排列，随 Appearance 字体和字号调整高度。常用 SVG 图形为 24px；独立图标按钮有至少 44×44px 点击区域和可访问名称。

标题通常可读两行，活动片段一至两行；详情显示经过同等权限过滤的完整内容。缩远时保留名称与状态，放大时展开片段。名称过长时可以查看全称。

单击选择节点，显示详情并突出相关线；“打开 Conversation”是明确的导航动作。键盘和列表视图提供等价路径。

### 5.2 连线

- 创建关系：细实线、带箭头的折线路径。卡片仍为直角，路径转折可以柔和处理。
- 通信关系：强调色虚线、方向箭头与计数标签。双向分别表示。
- 计数单位：当前筛选范围内**不同的投递身份**，不是 SSE 更新、流式文本块、工具调用数或模型 HTTP 次数。

记录因权限、分页或保留上限而不完整时，计数标成“已加载 N 条”等实际范围。先取得服务端授权的节点与边，再做布局、计数和搜索，避免通过统计暴露其他资源。

### 5.3 画布与个人整理

默认沿创建层级排布，独立协作成簇。用户可以平移、缩放、拖动节点，选择居中或聚焦。新活动更新内容与计数，保持已整理的位置；新成员在已知来源附近出现。

单条线提供“隐藏此连线”；节点提供“隐藏通信线”“隐藏全部关联线”。有已隐藏数量与恢复入口。偏好按当前人员与绑定图的稳定身份隔离保存；退出或撤权后终止旧观察并清理未授权的缓存显示。

图与日志各有明确筛选范围。图形隐藏是个人整理动作；日志只随其明确筛选改变。

## 6. 活动观测怎样得到

### 6.1 分开观察成员和运行

成员 `active` 表示处于可接纳阶段；原生 readiness 为 ready 也不说明正在生成。当前成员格子按 membership 表达可用性，新的活动卡片另取运行观测。

现有 `ConversationSnapshot.live` 提供 busy、当前 assistant message、工具 callId／name／status 等字段。它没有完整的结构化错误、明确的请求阶段或全量事件序列。实现时补足公开观测投影，在 adapter 内处理原生对象，外层收到冻结 DTO。

### 6.2 状态和原文片段

| 可证明的观测              | 卡片表现                      | 片段来源                         |
| ------------------------- | ----------------------------- | -------------------------------- |
| 当前模型请求正在等待输出  | Waiting for Model Response    | 已确认的请求阶段                 |
| 当前活动块为公开 thinking | Thinking... ＋前段            | 当前输出中的 thinking 文本       |
| 工具已经开始执行          | Tool using ＋工具名、参数前段 | 当前执行记录，以 callId 关联参数 |
| 当前活动块为回复文本      | 回复前段                      | 当前文本块                       |
| 工具在排队或构造调用      | 工具等待／准备中的实际状态    | pending 等明确观测               |
| 只有 busy，尚缺阶段细节   | Working，详情说明尚无阶段细节 | busy 观测                        |
| 空闲、已有回复            | Idle ＋最近回复前段           | 最近已提交回复，标明为上一条     |
| 空闲、尚无回复            | Idle                          | 空闲观测                         |

执行中的工具优先于已经输出的旧片段。多工具并行时显示一个可辨认的名称及“另有 N 个”，详情列出全部；前台输出变化时使用当前活动块，避免一直显示同一条消息中最早的 thinking。仅有内容块数组顺序或旧 thinking，不能证明当下仍在思考。

thinking 只使用 provider／公开 SDK 已提供、且当前人可读的内容。工具参数与回复片段采用相同资源的读取权限，渲染为转义文本；参数先做有界序列化，再按显示长度截取。

页面展示最近观测时间或 stale 状态。连接断开后卡片保留“上次观测”，恢复时重新授权并同步；断连自身不变成 Conversation 故障。Board 批量读有有限成员数和内容预算，详情与分页按需获取。

### 6.3 错误、故障和未知结果

| 事实                         | 显示与作用域                                       |
| ---------------------------- | -------------------------------------------------- |
| 已有结构化 HTTP 状态         | 例如 HTTP 429 · Too Many Requests，说明是哪次请求  |
| 已有公开错误码但无 HTTP 码   | 显示该真实错误码和可公开原因                       |
| 确认某个 Conversation 已故障 | Conversation crashed，关联该资源和可公开故障原因   |
| 单个工具返回错误             | Tool error ＋工具名；不据此断言 Conversation 崩溃  |
| Runtime／Session 级故障      | 工作台级故障提示，与每个 Conversation 状态分别呈现 |
| 连接中断或结果未知           | Disconnected／Result unconfirmed，保留原请求身份   |
| 成员已结束／退役             | 对应生命周期状态，依据可用能力提供历史入口         |

HTTP 状态、公开 RPC 错误码、投递 reason 和生命周期 phase 都保留来源。UI 不通过正则解析异常字符串来合成状态码或判断回滚。

卡片与详情只提供授权、脱敏后的公开信息；运维诊断中的完整错误有自己的访问渠道。provider key、私密 header、其他人路径和不可读内容不会因展开详情扩大可见范围。没有结构化错误码时说明“错误码未提供”。

## 7. 交流日志与发起者

每条交流由以下信息组成：投递身份、发送／接收 Conversation、发起方式、输入模式、可读正文、当前投递结果、已记录的关联以及有依据的时间。

**通信源与实际发起者分别记录。** 原生工具调用可以由 Agent 发起；人类也可以在成员面板通过某个 Agent 身份回复。后者显示为“某人经由 B 发送”，不会仅凭 source=B 归为 B 自主发言。只有真实调用／操作者记录可确认发起方式时才标注；旧资料不足则显示“发起方式未记录”。principal 是授权身份，不替代这项证据。

replyTo 仅在明确保存了关联时显示。B→C 与 C→B 可以组成双方往来，消息内容相似、时间相邻或一条回执 done 都不足以建立问答关联。

投递的 queued／placed／done／unanswered／unknown 保留原含义。done 表示该输入的生成终态；placed 不是已读确认，unknown 继续由原身份核对。外层 ExtensionOperation 完成时，内部回执仍可能未决。

列表支持按成员、方向、模式、发起方式、状态与可读文本筛选。时间来自实际记录，显示其含义：接纳时间、完成时间或记录时间；缺失则注明。分页有稳定 cursor 和范围说明，提供加载较早记录的入口。

节点、关系和记录首先经过当前权限过滤。不可读另一端的身份、名称、消息、数量和检索结果由服务端按既有策略处理，浏览器不补出不可见参与者。观察日志走只读权限，不向观察者授予 send／reply。Team chat 是人类侧聊，明确送入 Agent 后才产生那次独立输入。

## 8. Conversation 导航与控制

扩展已有公共 `navigate(AgentRef)`。当前宿主会在普通工作区 refs 中查找，MAS 成员来自另一 catalog，因此新的图还需要**通用、受授权的资源解析与打开链路**，同时覆盖历史、实时流、输入、配置与返回。

导航参数负责定位；宿主重新验证当前人、当前资源和最新引用，再开放相应能力。能够显示节点，不等于一定可看完整 transcript 或执行输入；可用操作由服务端明确返回和复查。旧引用只能帮助解析逻辑资源，不能继续作为旧授权使用。

资源提供者由可信服务端装配，通用打开链路保留原模块的权限检查。MAS 的通信／管理能力及 owner 检查，与当前人类的 read／send／manage 范围组合使用；把成员加入导航列表不能绕过这些检查。现有 `MasClient.configure` 仍是整组 profile 接口；为 MAS 成员开放独立 model／cwd 配置时，需要在其管理权边界内补齐对应端口。

图中的发送、steer、followUp、停止和退役复用受控端口。当前成员面板继续保留已有操作；图形改造时补齐未决操作的原身份读取、状态与交互锁定，不依靠“再试一次”解决未知结果。关闭界面或取消等待仅结束观察。

普通工作区当前明确提供归档／恢复；MAS 端有退役。用户需要的“用完删除”是普通 Conversation 的产品使用方式，物理删除、可恢复删除及审计记录保留需按实际删除契约实现，不能把现有归档或退役按钮改名就视为完成。

## 9. 数据接续与实现位置

下表是**拟补足的投影需求，不是新的已发布 API**：

| 需求               | 当前可用依据                                             | 接续工作                                     |
| ------------------ | -------------------------------------------------------- | -------------------------------------------- |
| 节点身份与成员资格 | MAS Member、ConversationRef                              | 按绑定来源合并，读取可用名称和最新引用       |
| 创建线             | spawn 的受控 source／创建链路；现有 parent 为 owner 投影 | 在实际创建边界保留可恢复来源，明确其记录时机 |
| 通信线             | CatalogDeliverySpec、DeliveryReceipt                     | 读取唯一投递，记录可公开时间、模式及内容位置 |
| 发起方式           | 人类绑定 actor 或原生 invocation                         | 把两者与 transport source 分开保留           |
| 回复关联           | reply 调用时持有的原 receipt ID                          | 明确保留关联，旧记录维持未记录               |
| 活动和故障         | ConversationSnapshot.live、原生公开观测                  | 增补有界、结构化、经权限过滤的投影           |
| 图到 Conversation  | 公共 navigate、普通工作区打开路径                        | 增补跨 catalog 的通用资源解析与能力检查      |
| 个人视图           | 当前人及绑定图                                           | 保存位置、隐藏、过滤与视口，不改变执行事实   |

记录优先沿现有受控持久化与投递路径增补；数据模型演进带版本和旧资料兼容。原生效果与附加观测可能跨不同提交边界，应分别表达结果。已经创建的成员或已接纳投递，即使附加记录缺失，也不能为补日志再次执行。图在资料不足时展示真实可用资源，并说明来源或关联未记录。

实现中的名称建议直接体现作用，如“membership”“activity”“delivery”“management source”。公共字段的改名需要版本兼容；内部可读性改进与用户文案可独立进行。

## 10. 手机、键盘和阅读

以 360×600、390×650 为默认最短手机目标。关系和交流使用视图切换；选中节点后用可展开详情和稳定的打开入口，保留画布空间。目录和模型交互继续在完整 Conversation 中完成。

成员列表与画布共享筛选、选择和权限，提供键盘／读屏等价路径。焦点可见，模态详情有焦点回绕、Escape 和返回；关闭后回到原触发位置。状态有文字，方向有名称，连线计数标签具有足够点击区域。

Appearance 的字体、字号和配色贯穿卡片、详情与日志。大字号使用换行、弹性高度和内部滚动，信息区与操作区均保持可达。

## 11. 用什么材料继续检验

### 设计推演

- 普通工作区与 MAS 名册出现相同 key／名称：资源仍按绑定来源和真实引用区分；进入 MAS 成员保留其原管理边界。
- B 的管理来源改变：创建记录、管理记录和历史来源各自保持含义。
- 人类经由 B 回复 C：通信方向仍为 B→C，同时显示人工发起。
- 一次投递先 queued 后 placed 再 done：数量为一次，回复关联仍等待独立证据。
- 切模型使 incarnation 改变：节点仍是同一 Conversation，旧动作失效，显示偏好保持。
- 工具失败、HTTP 429、Runtime 故障、断连、unknown：分别显示实际作用域和可恢复操作。
- 权限撤销与分页相交：发布前重新检查，后续页面与统计不泄漏新内容。

### 后续实现检验

使用真实 Pi 与本地确定性 provider，分别验证公共 DTO、授权与原请求恢复；再验证成员进入 Conversation、返回保持状态、两种手机视口和大字号。关系／日志计数以保存的唯一投递为依据，并保留正向触发及调用计数，避免只用“零请求”证明功能。

用户已经确认的本机五项继续有效。本轮是设计与针对性修订，后台 GUI 验收仍暂停。新图完成后的实操在用户明确恢复相应验收后进行。

## 12. 接续顺序

先确定受控来源、观测字段与导航契约，完成可读资源的贯通；再把真实节点、创建线、通信线和日志组成完整 A／B／C 使用路径。最后用筛选、隐藏、个人位置和手机布局处理实际协作规模。

这些工作沿用 P1 的受控服务与持久化、P2 的人员／资源过滤、P3 的通用扩展、P4 的 MAS 操作、P5 的 Conversation 界面，以及 P6 的版本化证据。设计稿使下一轮工作具体起来；已完成的各阶段继续按其实际内容和验收范围表述。
